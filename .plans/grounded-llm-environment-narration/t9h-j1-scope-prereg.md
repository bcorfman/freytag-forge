**Question.** If the J1 state (scene name plus starting place) is sent only for a relation whose place is the scene's own location, which is the case the drain miss came from, does the verifier (a) still accept present things at scene-level places, (b) reject missing, remembered, relocated and look-alike things at scene-level places and at specific places, and (c) leave every specific-place relation exactly as the current verifier asks it?

**Why this change (evidence already in hand, no new call).** The drain miss is an over-demanded location: a thing whose place is the whole scene (the park) is never described as "at the park", so the judge hedges. The J1 screen's rows show what J1m does outside that case. On the 38 reject-labelled look-alike samples in the T7 corpus (specific places such as "the carved mantel shelf"), J1m's mean score rose from 0.101 (V0) to 0.173, and 5 samples reached 0.5 or more under J1m against none under V0 (V0 maximum 0.48, J1m maximum 0.66). The extra `starting_places` entry restates the thing's name and place, and the judge appears to count a similar object sitting at that place as the thing. `a-022` was the highest of those, so it was the sample that crossed the line, not an isolated miss; `d-009` (silver badge) scored exactly 0.65 on both samples, which is not above the line, so it stayed uncertain. Specific-place relations gain nothing from J1 (V0 had 0 false rejects of 204 on the corpus). So the change is subtractive: stop sending J1 where it is not needed.

**The rule under test (J1c).** For each relation, if `relation.place` equals the scene's own location, the request is the J1m request (J0 question unchanged; state `{"narration", "scene", "starting_places": {thing: place}}`). Otherwise the request is the V0 request (state `{"narration"}`). A relation held by someone is never a scene-level relation. The product knows the scene's location (`scene.metadata.location_id`); wiring that comparison is a later step. In this screen each fresh case carries an authored `scene_place` field and the harness compares it with `relation.place` by exact string.

**What is run.** Two arms are asked, `V0` and `J1m`, exactly as in the J1 screen. J1c is not a third arm: each J1c verdict is read from the J1m row when the case is scene-level and from the V0 row when it is specific-place. Those requests are identical to the ones J1c would send, so no extra calls are needed and the J1c result is the same as running it. A unit test (free, in the build) asserts that the harness's J1c payload equals the V0 payload whenever `place` differs from `scene_place`, and equals the J1m payload otherwise.

**Set 1: the T7 corpus is not rerun.** The corpus has no scene locations, so under J1c every corpus relation is a specific-place relation and J1c sends the V0 request for all 274. The 2026-10-29 rows already hold V0 on that corpus under Jev `jev-1.13.0` / `observation-relation-v1`: zero false accepts (C1), zero false rejects of 204 (C2), 2 strict failures of 204 (1.0%, limit 5%). Those rows carry the T7 gate for J1c. Limit: the corpus cannot exercise the scene-level path, and a change of Jev model or version between that run and this one is reported and voids this carry-over.

**Set 2: fresh cases (frozen before any score).** `scripts/ringer/environment_narration/j1_scope/cases.jsonl`: 60 cases in 6 new stories, none of the 8 T7 stories, not the park story, not the 5 held-out stories of the J1 screen. 10 cases per story, each with one relation `{thing, place, holder: null}`, a `scene` title, a `scene_place` and a 3 to 5 sentence plain third-person past-tense narration:

| group | per story | what |

| scene-level | 2 | negative `lookalike`: one plain, one explicit-contrast ("not a <thing>", "no <defining feature>") |

| specific-place | 1 | negative, rotating `missing`, `remembered`, `elsewhere` (each twice over the set) |

Totals: 24 positives (12 scene-level, 12 specific-place) and 36 negatives (12 scene-level and 12 specific-place look-alikes, 6 and 6 others). Authoring rules, checked by script: a scene-level positive never contains its place string (case-insensitive substring); a `missing` narration never mentions the thing; `remembered` shows it only in memory or as absent; `elsewhere` shows it present at a different named place in the same story; a `lookalike` names a similar but different object, and the explicit-contrast kind says in words that it is not the named thing; the explicit-contrast narrations are written fresh and must not copy the wording of the corpus cases `a-022` or `d-009`. A worker authors the cases from this table; I hand-read all 60 before the lock; any change is made before the lock, never after. **Reading the outcomes.**
- All gates pass: supports wiring J1c into the product's verifier behind the enforcement flag (the scene name and `scene.metadata.location_id` from the validated current scene). It does not qualify enforcement, which still needs a fresh enforced stage run under its own preregistration.
- F1 fails on a scene-level negative: the J1 state is not safe even where it is needed; the verifier keeps its current state and the drain miss stays open.
- F1 fails on a specific-place negative: V0 itself leaks on fresh cases; reported as a separate verifier finding, and J1c is not wired until it is understood.
- F2 or F3 fails alone: no wiring; the report names which group missed.

**Limits.** Sixty cases in six stories, authored by one worker and read by me, not blind; the effective n for rates is the case count (36 negative cases), so zero accepts bounds the true negative-accept rate only to about 8% at 95% confidence, which is why the gate also lists near-misses by score. The corpus carry-over rests on one earlier run. The fresh scene-level places are authored fields; whether the product's `scene.metadata.location_id` equals a thing's declared place often enough to trigger the J1 path is a wiring question this screen does not answer.
