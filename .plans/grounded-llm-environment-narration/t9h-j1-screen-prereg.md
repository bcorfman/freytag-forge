# T9h route E J1 screen: frozen T7 corpus plus fresh held-out scene-level cases (preregistration, DRAFT, nothing billed)

Status: held-out set frozen 2026-10-29 (SHA-256 `667593d2670d65127e0436759374d5d8aa47b459e6d7c54dbe842883845f4ee9`, `j1_screen/lock.json`); billed run awaits Brandon's go. Drafted 2026-10-29 after the drain probe (`t9h-drain-question-prereg.md`, J1 passed 30 of 30 positives and 0 of 30 negatives on one drain). That screen cannot qualify a changed verifier. This one reruns the frozen T7 corpus and a fresh held-out set before any enforcement change. The harness and the held-out cases are built free; the billed run needs Brandon's go.

**Question.** Does giving the judge the scene name and each required thing's starting place (the J1 state) (a) keep the T7 gate on the frozen corpus, with no new false accepts, and (b) still accept present things whose place is the whole scene, on cases the drain probe did not see, without accepting missing, remembered, relocated or look-alike things?

**What changes from the drain probe, and why.** The product sends one batched Jev request per narration attempt, with one question per required relation and one shared state. A single `starting_place` key cannot serve two relations. So the arm under test, `J1m`, uses the J0 question text unchanged and the state `{"narration": ..., "scene": <scene>, "starting_places": {<thing>: <starting place>, ...}}`, with one entry per relation that has a place and no entry for a relation held by someone. This map is a new wording of the J1 idea and is itself under test here.

**Arms (same thresholds as T7: accept above 0.65, reject below 0.35; same Worker `/jev` route).**
- `V0 current`: the product's own request for the case: `_question_for(relation)` per relation and state `{"narration": ...}`.
- `J1m`: as above.

**Set 1: the frozen T7 corpus.** `scripts/ringer/environment_narration/verifier_corpus/cases-{a,b,c,d}.jsonl`, 224 cases, 274 relations, combined SHA-256 `1f18f4b41778876b7c5066a1a3d75e9db910d075e8c1ee337ab5b79b0641dc52` (the T7 lock; `--run` refuses on a mismatch). One batched request per case, as in T7. The corpus has no scene titles, so `scene` is the case's `story` value (for example "frontier town"); this is a stand-in, stated as a limit. `starting_places` takes each relation's `place` when it has no holder. Reject-labelled relations keep their label: the permitted place is the starting place, and a wrong-place or look-alike narration must still be rejected.

**Set 2: held-out scene-level cases (frozen before any score).** `scripts/ringer/environment_narration/j1_screen/heldout.jsonl`: 40 cases in 5 fresh stories (none of the 8 T7 stories, not the park story), 8 per story: 4 positives, then one negative each of `missing`, `remembered`, `elsewhere` and `lookalike`. Each case has one relation `{thing, place, holder: null}` whose place is the scene itself (a park, a plaza, a workshop floor), a `scene` title, and a 3 to 5 sentence plain third-person past-tense narration. Authoring rules, checked by script: a positive never names its starting place (case-insensitive substring), so the place is only the scene, as in the recorded drain replies; a negative `missing` never mentions the thing; `remembered` shows the thing only in memory or as absent; `elsewhere` shows the thing as present at a different, named place in the same story; `lookalike` shows a similar but different thing. Labels follow from construction. I hand-read all 40 before freezing. One change was made before the lock: the authoring worker had used a wide area as each story's place (for example 'the lighthouse island') while the scene was a sub-area, which made every `elsewhere` label wrong (the thing was elsewhere on the same island), so each story's place was set to the scene location itself ('the keeper's yard', 'the docking ring', 'the east market', 'the sample clearing', 'the main auditorium'). Positives still never contain it; any case I change is changed before the lock, never after. The cases are plain and short (3 sentences each, not the 3 to 5 asked). The set is locked by SHA-256 in `j1_screen/lock.json`; `--run` refuses on a mismatch.

**Counts and cost.** Set 1: 224 cases x 2 arms x 2 samples = 896 requests. Set 2: 40 cases x 2 arms x 5 samples = 400 requests. Total **1,296 Jev requests**, fixed-seed order, arms interleaved, no retries, no replacement samples. Ceiling to be printed by `--dry-run` (T7's 448 requests were about $0.008, so expect about $0.02); `--max-calls 1300 --max-usd 0.05` (dry run: ceiling $0.0235). Stops after 3 consecutive unusable replies or on HTTP 429/5xx.

**Gate (J1m must pass all four; V0 is reported beside it).**
- C1 (corpus, T7 gate 1): zero false accepts over the reject-labelled relation samples, in both samples.
- C2 (corpus, T7 gate 2): false rejects (label accept, verdict reject) at most 5% of accept-labelled relation samples excluding `invention_unreported`; strict failures (uncertain, unavailable and reject) also at most 5%.
- H1 (held-out): zero accepts among the 100 negative samples.
- H2 (held-out): at least 90 of the 100 positive samples are `accept` (uncertain counts as a failure) and no fewer than V0's.
Report also: per category and per story, every false row listed, sample-to-sample disagreement, latency p50 and p95, model and version. If J1m fails C1 or H1, the verifier keeps its current state and the drain miss stays open.

**Limits.** Forty held-out cases in five stories, authored by one worker and read by me, not blind; the effective n for rates is the case count, not the sample count (the two T7 samples agreed on every relation). The corpus `scene` is the story name, not a product scene title. Single-thing held-out requests, while corpus cases batch up to several relations. A pass would support wiring the J1m state into the product's verifier behind the enforcement flag; it would not qualify enforcement, which still needs a fresh enforced stage run under its own preregistration.
