# Grounded turn-contract plan

Facts remain the sole authority for consequential world state. The model may author intent, dialogue, framing, and atmosphere, but every material state assertion it stages is a typed claim that must agree with post-effect facts.

## Phase 0 — Baseline and boundary audit

1. [x] Document proposal/rendering entry points.
2. [x] Add deterministic contradictory-material baseline coverage.
3. [x] Record normal-turn provider-call and latency baseline.
4. [x] Classify structural, temporary prose, and presentation checks.

**Exit criteria:** [x] the gap is measured across every adapter without a story-specific implementation decision.

## Phase 1 — Typed contract and candidate-state validator

1. [x] Add typed `staging_claims` to local turn/action contracts and carry it through supported normalized provider envelopes.
2. [x] Define closed generic relation/ID vocabulary; reject malformed, unknown, duplicate/contradictory, and observer-invisible claims.
3. [x] Validate claims against a clone after the validated proposal effects have been applied, without mutating the source state.
4. [x] Keep parsing and semantic validation local; provider JSON mode remains syntax assistance only.
5. [x] Route claim failures through the shared recovery request and raise `ORDINARY_TURN_RECOVERY_EXHAUSTED` with no commit after exhaustion.

**Exit criteria:** [x] custody, environment, access, and event claims validate against candidate facts with no narration-text matching.

## Phase 2 — Generic policy/data support

1. [ ] Realize consequential environmental package declarations as facts.
2. [ ] Add generic environment-transition policy support.
3. [ ] Add bounded dramatic consequence classes.
4. [ ] Validate route/evidence viability under complications.
5. [ ] Exercise declarative paths in mystery, fantasy, and two more genres.

## Phase 3 — Planner and renderer integration

1. [ ] Supply observer-scoped legal claim/effect context to the planner.
2. [ ] Add planner instruction examples distinguishing atmosphere and staging.
3. [ ] Render only accepted proposal prose after atomic commit.
4. [ ] Remove the temporary phrase-based custody guard after parity coverage.

## Phase 4 — Evaluation, persistence, and deployment adapters

1. [ ] Build a cross-genre relation-family matrix and adversarial fixtures.
2. [ ] Verify persistence projections and both web adapters end to end.
3. [ ] Record staging request IDs, retries, latency, and fail-closed evidence.

## Phase 5 — Rollout and cleanup

1. [ ] Gate the new contract during its initial staging window.
2. [ ] Compare staging metrics with the Phase 0 baseline.
3. [ ] Promote only with bounded recovery, latency target, and 90% coverage.
4. [ ] Remove compatibility paths and update remaining authoring/runtime docs.
